# PART A — BACKEND (REST API)
# ═══════════════════════════════════════════════════════════════

## A1. PROJECT TYPE

Build a **Modular Monolithic REST API** using clean architecture inside a single deployable backend.

- One codebase, one deployment
- Domain logic split into independent modules
- Each module follows the same structure and conventions
- APIs consumed by a separate frontend
- Goal: production-ready, maintainable, easy to extend

---

|-------|------------|

| Language | TypeScript (strict mode) |
| Framework | Fastify |
| ORM | Prisma |
| Database | PostgreSQL |
| Validation | Zod |
| Authentication | JWT Access Token + Refresh Token |
| Password Hashing | bcrypt |

| API Docs | Swagger / OpenAPI at `/docs` |
| Testing | Vitest |
| Linting | ESLint |
| Formatting | Prettier |

Adapt stack only when the user specifies otherwise. Keep the same architectural patterns even if technologies change.

## A4. MODULE STRUCTURE (Mandatory — Every Module)

```
{module}/
├── {module}.controller.ts
├── {module}.service.ts
├── {module}.repository.ts
├── {module}.routes.ts
├── {module}.schema.ts
├── {module}.types.ts
└── {module}.mapper.ts
```

### Layer Responsibilities

| Layer | Responsibility | Must NOT contain |
|-------|----------------|------------------|
| **Routes** | HTTP method, path, auth, OpenAPI schema, wire DI | Business logic |
| **Controller** | Parse request, call service, return response | Business logic, DB access |
| **Service** | Business rules, transactions, duplicate checks, calculations | HTTP logic, direct Prisma |
| **Repository** | Prisma CRUD and queries only | Business logic |
| **Schema** | Zod schemas for body, params, query | — |
| **Mapper** | DB model → API response DTO | Business logic |
| **Types** | Request/response interfaces | — |

---

## A5. REQUEST FLOW

```
HTTP Request → Routes → Controller → Zod Validation → Service → Repository → Prisma → DB → Mapper → Response
```

Never skip layers. Never put business logic in controllers or repositories.

---

## A6. DEPENDENCY INJECTION

Wire in routes file:

```typescript
const repository = new ModuleRepository(app.prisma);
const service = new ModuleService(repository);
const controller = new ModuleController(service);
```

Use constructor injection. Pass `app.prisma` from the Prisma plugin.

---

## A7. API RESPONSE FORMAT

### Success
```json
{ "success": true, "data": {} }
```

### Error
```json
{ "success": false, "message": "Human-readable error message" }
```

### Validation Error
```json
{ "success": false, "message": "Validation failed", "errors": ["field: detail"] }
```

Use shared helpers: `successResponse(data)`, `errorResponse(message, errors?)`.

Return `201` on create. Use 400, 401, 403, 404, 409, 500 appropriately.

---

## A8. ERROR HANDLING

- Centralized error handler plugin
- Throw `AppError` from services: `message`, `statusCode`, optional `errors[]`
- `ZodError` → 400 with field errors
- Prisma `P2002` → 409, `P2025` → 404
- Never expose stack traces in production
- Never log passwords or tokens (use logger redact)

---

## A9. VALIDATION (Zod)

- Validate every endpoint: `body`, `params`, `query`
- Never trust client input
- Schemas in `<module>.schema.ts`
- Types via `z.infer<typeof schema>`
- Parse in controller: `schema.parse(request.body)`

### Pagination (all list endpoints)

Query: `?page=1&limit=20&search=&sortBy=&order=asc`

Response:
```json
{
  "success": true,
  "data": {
    "items": [],
    "meta": { "page": 1, "limit": 20, "total": 0, "totalPages": 0 }
  }
}
```

Defaults: `page=1`, `limit=20`, `order=asc`, max `limit=100`.

---

## A10. AUTHENTICATION & AUTHORIZATION

### JWT
- Access token: short-lived (e.g. 15 minutes)
- Refresh token: long-lived (e.g. 30 days), stored hashed in DB
- Payload: `{ id, ...userClaims, role }`
- Hash passwords with bcrypt

### Auth Endpoints
```
POST /auth/login     → access + refresh tokens + user profile
POST /auth/refresh   → new access + rotated refresh token
POST /auth/logout    → revoke refresh token
```

### Protection
- `authenticate` middleware on protected routes
- Role-based guards (e.g. `requireRole('ADMIN')`) per route
- `preHandler: [authenticate]` in route definitions
- Document bearer auth in OpenAPI

Define roles per project: `{ROLE_1}`, `{ROLE_2}`, etc.

## A11. DATABASE & PRISMA

- PostgreSQL
- All changes via Prisma migrations
- Avoid raw SQL unless necessary
- Use transactions for multi-step operations
- Seed: admin user, lookup data, sample records
- Serialize BigInt IDs as strings in responses

```bash
pnpm prisma migrate dev
pnpm prisma generate
pnpm prisma db seed
```

## A12. REST API CONVENTIONS

### Standard CRUD
```
GET    /{resources}          # List (paginated, searchable)
GET    /{resources}/:id      # Get one
POST   /{resources}          # Create
PATCH  /{resources}/:id      # Partial update
DELETE /{resources}/:id      # Delete
```

### Naming
- Plural, kebab-case paths: `/order-items`, `/user-profiles`
- `PATCH` for partial updates, not `PUT`
- Shared `parseIdParam()` for numeric IDs

### Utility Endpoints
```
GET /health       → { success: true, data: { status: "ok" } }
GET /docs         → Swagger UI
GET /docs/json    → OpenAPI JSON
```

### Custom Actions (when needed)
```
POST /{resources}/:id/{action}    # e.g. approve, publish, archive
GET  /{resources}/{view}          # e.g. calendar, summary, report
```

- Auto-generate from route schemas

## B5. DATA FLOW

```
User Action → Page/Component → Feature Hook → Feature API → API Client → Backend → Response → Cache/UI Update → Toast
```

Never call `fetch` in components. Always: `api.ts` → `api-client.ts`.

---

## B6. API CLIENT

### Shared Types
```typescript
interface ApiSuccess<T> { success: true; data: T; }
interface ApiError { success: false; message: string; errors?: string[]; }
interface PaginatedData<T> { items: T[]; meta: PaginationMeta; }
```

### Rules
- Base URL from `NEXT_PUBLIC_API_URL`
- Attach `Authorization: Bearer <token>` on protected requests
- On 401: refresh token once, retry request
- Refresh fails → clear auth, redirect to `/login`
- Throw typed errors with `message`, `status`, `errors[]`

---

## B7. AUTHENTICATION (Frontend)

### Login
1. Submit credentials → `POST /auth/login`
2. Store tokens + user profile
3. Redirect to home/dashboard

### Refresh
- On 401 or before expiry → `POST /auth/refresh`
- Rotate both tokens; queue concurrent requests during refresh

### Logout
1. `POST /auth/logout`
2. Clear storage
3. Redirect to `/login`

### Auth Provider
```typescript
{ user, isAuthenticated, isLoading, login(), logout() }
```

### Route Protection
- `(app)` group requires auth
- Unauthenticated → `/login`
- Authenticated on `/login` → redirect home

### Role-Based UI
- Hide nav items and actions user cannot access
- Frontend guards are UX only — backend always enforces auth

- React Hook Form + Zod resolver
- Schemas in `features/{feature}/schemas.ts`

- Show Zod errors + API `errors[]` on fields

## B9. LIST PAGES (Standard Pattern)

Every list page MUST have:

| Feature | Implementation |
|---------|----------------|
| Data table | TanStack Table, sortable columns |
| Pagination | Controls from `meta.totalPages` |
| Search | Debounced input → `?search=` |
| Page size | Select (10, 20, 50) |
| Loading | Skeleton or spinner |
| Empty | Message + create CTA |
| Error | Message + retry |
| Actions | View, Edit, Delete (confirm dialog) |
| Create | "Add New" → `/{resource}/new` |

```typescript
const [page, setPage] = useState(1);
const [limit, setLimit] = useState(20);
const [search, setSearch] = useState('');
const debouncedSearch = useDebounce(search, 300);
const { data, isLoading, error } = useResources({ page, limit, search: debouncedSearch });
```

## B20. HOW TO ADD A NEW FRONTEND FEATURE

1. Create `features/{module}/` (api, hooks, schemas, types, components)
2. Types must match backend DTOs exactly
3. API functions: list, getById, create, update, delete (+ custom actions)
4. TanStack Query hooks with query key factory

## B21. FRONTEND — WHAT NOT TO DO

- No direct `fetch` in components
- No mismatched types vs backend
- No insecure token storage
- No missing loading/empty/error states
- No hardcoded API URLs
- No business logic in components
- No inconsistent UI across modules
- No frontend-only auth (backend must enforce)
- No pages without backend endpoints

## C7. INSTRUCTION FOR AI

When building any project with this template:

1. Ask for or infer `{PROJECT_NAME}`, `{DOMAIN_MODULES}`, `{ROLES}` if not provided
2. Read existing code before changing anything
3. Keep backend module and frontend feature names identical
4. Implement full vertical slices: DB → API → UI → tests
5. Backend and frontend types must match exactly
6. Prefer small focused diffs
7. Do not add unrequested features
8. Do not break established patterns

### Per-feature workflow
1. Prisma model + migration
2. Backend module (7 files)
3. Frontend feature (api, hooks, schemas, types, components, pages)
4. Navigation + tests
5. Verify end-to-end

This is a generic architecture template. Apply domain-specific business rules only as defined by the user for each project.
